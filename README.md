# Планирование закупок: обезличенный датасет

Дистрибьютор инструмента и оборудования (Румыния). Данные выгружены из ERP,
обезличены и предназначены для разработки модели планирования закупок.

## Задача

Спланировать закупку по каждому SKU так, чтобы:

1. **Плечо поставки — по истории поставщика.** Почти весь ассортимент импортный (Азия,
   морем). Заказ, размещённый сегодня, встаёт на склад через ~4–6 месяцев,
   поэтому решение принимается против прогноза спроса на горизонте
   «плечо + период покрытия», а не против текущих продаж.
   По факту (см. `purchase_orders.csv`): медиана планового плеча **123 дня**,
   p25 = 52, p90 = 205. Плечо в расчёте может превышать 180 дней.
2. **Учтена сезонность.** Категории в наборе намеренно разной формы:
   `space_heaters` — 42% годовых продаж в октябре, `string_trimmers` — пик в
   мае, `sanitary_faucets` — ровный спрос. Заказ по среднемесячным продажам
   ломается на всех троих по-разному.
3. **Учтено уже заказанное.** По части SKU уже есть открытые заказы
   поставщику с плановой датой прихода (`status = open`), их количество нельзя
   заказывать повторно.
4. **Отсечение по рентабельности.** Товар с низкой наценкой не должен
   попадать в закупку автоматически — он идёт в отдельный список на
   пересмотр цены или вывод из ассортимента.
   Параметр: **`MIN_MARKUP_PCT = 25`** (средняя наценка к себестоимости за
   последние 12 мес). Ниже порога сейчас 68 SKU из 413 продававшихся.

## Файлы

Все таблицы связаны по `sku_id`. Кодировка UTF-8, разделитель `,`.

`export_meta.json` рядом с таблицами задаёт дату среза в поле `cutoff_date`
в формате `YYYY-MM-DD`. При отсутствии файла берётся последний день
последнего полного месяца продаж, и отчёт содержит предупреждение.

Чтобы собрать пробный отчёт, установите пакет командой `python -m pip install .`
и выполните из каталога с выгрузкой:

```python
from purchase_planning import plan, write_report
from purchase_planning.sku_labels import load_sku_labels

write_report(plan("."), "order.xlsx", sku_labels=load_sku_labels("."))
```

### `sku_dim.csv` — справочник товаров (791 строка)

| Колонка | Смысл |
|---|---|
| `sku_id` | ключ товара |
| `category` | одна из 6 категорий |
| `brand_id`, `supplier_id` | обезличенные бренд и основной поставщик |
| `supply_type` | `import` / `local` / `unknown` (нет истории приходов) |
| `uom` | единица (`pcs`, `set`) |
| `weight_kg` | вес единицы — для расчёта объёма контейнера |
| `warranty_months` | гарантия |
| `target_cover_days` | целевое покрытие в днях, заведённое в ERP (часто 0 = не задано) |
| `price_decile` | дециль цены **внутри своей категории** (1 = дешёвые, 10 = дорогие) |
| `first_sale_month`, `last_sale_month`, `months_with_sales` | история активности |
| `qty_total` | суммарно продано штук за всю историю |
| `avg_markup_pct_12m` | средняя наценка к себестоимости, %, взвешенная по количеству; **пусто = не продавался последние 12 мес** (378 SKU — это мёртвый ассортимент, его тоже надо распознать) |
| `on_order_qty` | штук в открытых заказах поставщику |
| `created` | месяц заведения карточки |

### `sales_monthly.csv` — продажи помесячно (37 414 строк)

`sku_id`, `category`, `month` (`YYYY-MM`), `qty_sold`, `qty_returned`,
`orders_cnt`, `markup_pct`, `partial_month`.

- Календарь **плотный**: строка есть на каждый месяц начиная с первого месяца
  продаж SKU. Отсутствие продаж — это честный `qty_sold = 0`, а не пропуск.
- `markup_pct` — наценка к себестоимости за месяц, %. Пусто, если продаж не
  было или себестоимость в ERP не проставлена.
- `partial_month = 1` — последний месяц выгрузки неполный, в расчёт средних
  не брать.
- Период: **2020-11 … 2026-08** (69 месяцев, ~5 полных сезонных циклов).

### `stock_monthly.csv` — остаток на 1-е число (9 627 строк)

`sku_id`, `month`, `stock_qty`. **Только с 2024-01** — раньше снимков нет.

Зачем: продажи ≠ спрос. Месяц с нулевыми продажами при нулевом остатке — это
упущенный спрос, и учить на нём модель как на «спроса нет» нельзя.

### `purchase_orders.csv` — заказы поставщикам (660 строк)

`po_id`, `sku_id`, `supplier_id`, `supply_type`, `order_date`,
`promised_date`, `planned_lead_days`, `status`, `qty_ordered`,
`qty_confirmed`, `qty_received`, `qty_pending`.

- `status`: `open` — заказ размещён, ещё не закрыт (57 строк, из них 22 с
  датой прихода в будущем, 17 127 штук в пути); `completed` — исполнен
  полностью; `closed` — закрыт (часто частично исполненным, сравнить
  `qty_ordered` с `qty_received`).
- Разница `qty_ordered` / `qty_confirmed` / `qty_received` — материал для
  модели надёжности поставщика: заказали одно, подтвердили другое,
  приехало третье.

### `receipts.csv` — фактические приходы на склад (2 394 строки)

`sku_id`, `receipt_date`, `qty`, `supplier_id`, `supply_type`. История
с 2020-11 — восстанавливает реальный ритм пополнения и партионность.

### `supplier_dim.csv` — поставщики (39 строк)

`supplier_id`, `supply_type`, `receipts_cnt`, `skus`,
`median_days_between_receipts`, `median_planned_lead_days`.

## Что обезличено

- Коды товаров, поставщики, бренды, номера заказов заменены на
  стабильные псевдонимы (`SKU-`, `SUP-`, `BRD-`, `PO-`). Один и тот же товар
  во всех файлах имеет один и тот же `sku_id`.
- Названия товаров, названия поставщиков, имена сотрудников и клиентов,
  ссылки на фото — **не выгружались вообще**.
- Названия категорий заменены нейтральными английскими ярлыками.
- **Денежных сумм в наборе нет.** Экономика представлена только процентом
  наценки и децилем цены внутри категории.

## Ограничения данных (важно для модели)

- Продажи — **суммарные по всем каналам** (опт, розница, маркетплейс). Для
  закупки это и нужно (общий спрос), но разложить по каналам нельзя.
- Наценка считается нетто к нетто (без НДС). Логистика, растаможка и хранение
  в неё **не входят** — это наценка на закупочную цену, а не итоговая маржа.
- Возвраты вынесены в `qty_returned` и **не вычтены** из `qty_sold`.
- У 153 SKU нет истории приходов (`supply_type = unknown`) — продавались
  с остатков, заведённых до начала выгрузки.
- 2026-08 — неполный месяц (данные на 13-е число).

### Статический отчёт

`python -m purchase_planning.backtest .` рассчитывает скользящий бэктест и
сохраняет метрики и квантили в `backtest.json` рядом с CSV. В репозитории
есть результат для обезличенной выгрузки. Для другой выгрузки укажите её
каталог. Если подходящего файла или квантиля группы нет, целевой запас
равен прогнозу на горизонт и отчёт показывает предупреждение.

`python -m purchase_planning.runs . --stub-llm` сохраняет `index.html` и
`report.xlsx` в одном каталоге запуска под `.scratch/purchase-runs/`.
Для просмотра откройте `index.html` в браузере.

### Публикация пилота

1. После слияния PR откройте **Settings → Pages → Build and deployment** и
   выберите **GitHub Actions** в поле **Source**. Если окружение
   `github-pages` защищено правилами веток, разрешите публикацию из `main`.
2. Для пояснений откройте **Settings → Secrets and variables → Actions** и
   добавьте секрет репозитория `EXPLABS_API_KEY`. По умолчанию используется
   `claude-sonnet-5`. Модель можно изменить переменной `EXPLABS_MODEL`.
   Переменная `LLM_MAX_SKUS` задаёт максимум SKU для пояснений, по умолчанию 300.
   В пояснения попадают SKU с наибольшим количеством к заказу в штуках. Значение `0` отключает пояснения по SKU.
   Пояснения запрашиваются пакетами до 40 SKU одного поставщика, сводка
   изменений — отдельно. Публикуются фразы, которые прошли проверку. Без
   ключа дашборд собирается без пояснений. В выводе запуска и `run.json`
   видны количество пояснённых SKU и причины пропусков.
   [Каталог Experiential](https://platform.experientiallabs.ai/models/claude-sonnet-5)
3. Загрузите шесть обезличенных CSV из ERP в `inbox/` ветки `main` одним
   коммитом. Портал определит дату среза по последнему полному месяцу продаж.
   Для ручного пересчёта выберите
   **Actions → План закупок и Pages → Run workflow → main**.
4. Откройте ссылку на сайт из завершённого запуска. Workflow проверяет, что
   Pages отдаёт собранную страницу с ожидаемой датой среза.
   [Документация GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

Actions обрабатывает запуски по одному. Workflow берёт выгрузку из коммита,
который его запустил, и историю из актуального `main`. Каждый расчёт
пересчитывает бэктест и коммитит `runs/<номер>/` с результатом, сравнением,
параметрами, хешем выгрузки и версиями входа и кода. Из истории берутся
сегменты для гистерезиса. На сайте есть ссылки на предыдущие отчёты.
Некорректная выгрузка останавливает запуск до коммита и публикации.
Повторная загрузка тех же файлов отклоняется, ручной запуск разрешает
пересчёт. Повтор попытки уже сохранённого запуска использует его результат,
если он остаётся последним. Запуск с выгрузкой из более раннего коммита
не заменяет уже обработанную свежую выгрузку.

CI проверяет workflow и расчёт, затем сохраняет сайт с тестовой выгрузкой и
заглушкой шлюза как артефакт `purchase-dashboard`.
